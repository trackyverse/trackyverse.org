Code Formatting for Developers

Introduction

For developers, the Trackyverse uses Air as a default formatter/linter to quickly reformat code. This article providers instructions on why we use Air and how to setup Air whether you are using RStudio, VS Code, or Positron.

Air shares properties with other modern formatters and linters, such as Ruff for Python.

A few things to note about Air:

  • Air is highly opinionated and offers relatively few options for customization but it can be customized.
  • Air is written in Rust and is based on the Biome formatter engine, which makes it extremely fast.

Formatting

Why does formatting matter? and why does using a linter matter?

Formatting code creates consistency in the style of the code written. It does not change the meaning of code, but instead allows for easier readablity and reporduciblity. Consistency, readability, and reproducibility are highly important for coding projects in general but become of even greater importance when projects have multiple developers.

Using a common linter matters because it enforces adhering to a given style. An agreed-upon set of rules are applied to all files of a particular type e.g., .R. A linter applies these rules every time a file is saved which streamlines the overall use of a given style.

For example, a prescribed style could recommend including whitespace after arguments (e.g., c(1, 2, 3) versus c(1,2,3)), enforce newlines after function closures, and all manner of rules and standards. Rules about code indenting with the appropriate amount of leading whitespace depending on the context. For more information about formatting and style details of Air see Air formating details

To understand the linting rules that are enforced by Air see How does Air format my code?

Installation

Trackyverse packages recommend using Air as a linter and formatter to enforce the standard style across all changes you make to your code / files.

To install Air at the command line, you can use one of the following commands.

On macOS and Linux:

curl -LsSf https://github.com/posit-dev/air/releases/latest/download/air-installer.sh | sh

On Windows:

powershell -ExecutionPolicy Bypass -c "irm https://github.com/posit-dev/air/releases/latest/download/air-installer.ps1 | iex"

This will automatically add Air to your PATH. The very first time you install Air, after adding it to your PATH variable with the command above, you’ll need to restart your terminal.

For a specific version of Air:

curl -LsSf https://github.com/posit-dev/air/releases/download/0.9.0/air-installer.sh | sh

powershell -ExecutionPolicy Bypass -c "irm https://github.com/posit-dev/air/releases/download/0.9.0/air-installer.ps1 | iex"

If you’re on macOS and are familiar with Homebrew, which we highly recommend, you can alternatively install the Air formula with:

brew install air

If you use uv, you can install Air via the air-formatter package:

# Global install
uv tool install air-formatter
air format path/to/my/script.R
# Invoke once without installing
uvx --from air-formatter air format path/to/my/script.R

Note that if you’d like to use Air inside of IDEs like VS Code or Positron, install the Extension for those editors, which comes pre-bundled with an Air binary, so there’s nothing you need to do besides download the Extension.

Setup

RStudio

If you are using RStudio, it does not support Language Server Protocol, but you can still use Air as an external formatter.

To get Air working with RStudio see the following guide - using Air with RStudio, which details how to adjust RStudio’s Global Options to find and recognize Air. See Guide to using Air below.

Positron and VS Code

If you are using Positron or VS Code, it does support Language Server Protcols and allows for Air to have a bit more freedom, enforcing different settings at a user level and at a workspace level (i.e. for just the current project you are working on).

Because Air can leverage Language Server Protcols there is no further setup needed.

Initialization

To setup Air for a repository, once installed, you can run the following code:

install.packages("usethis")

We can then use {usethis} to setup Air for a repository:

usethis::use_air()

This will create a air.toml file and a folder .vscode wherein it will create two config files: settings.json and extensions.json.

The settings.json file contains the following:

{
    "recommendations": [
        "Posit.air-vscode"
    ]
}

The extensions.json file contains the following this:

{
    "[r]": {
        "editor.formatOnSave": true,
        "editor.defaultFormatter": "Posit.air-vscode"
    },
    "[quarto]": {
        "editor.formatOnSave": true,
        "editor.defaultFormatter": "quarto.quarto"
    }
}

Both settings.json and extension.json can be further customized such as:

{
    "[r]": {
        "editor.formatOnSave": true,
        "editor.defaultFormatter": "Posit.air-vscode"
    }
}

Guide to using Air

Once we have setup Air on a repository we can do a couple different things to start using it with our code.

RStudio

To enable features such as Format on Save we can adjust the Global Settings using Tools -> Global Options -> Code -> Saving and check Reformat documents on save., which is detailed in Air’s guide to using with RStudio.

Positron and VS Code

To enable features like Format on Save, you’ll need to adjust settings in either your user or workspace level settings.json file. We generally recommend modifying workspace level settings for two reasons:

  • Workspace level settings exist inside your workspace folder at .vscode/settings.json and are checked in to your version control system. This means that your collaborators will get those settings automatically when they check out your project. User level settings are not checked in to version control.

  • User level settings are automatically applied for all projects that you open. While this sounds nice, if you open an older project (or a project you don’t own) that doesn’t use Air, then you’ll have to remember to turn off your user level Air settings before committing to that project, otherwise you may create a large amount of format related diffs that the project may not want.

The easiest way to set up a workspace level settings.json with the recommended settings is by running the command Air: Initialize Workspace Folder. This is equivalent to running usethis::use_air() from an R console.

Alternatively, to open your settings.json file from the Command Palette (Cmd + Shift + P on Mac/Linux, Ctrl + Shift + P on Windows):

Run Preferences: Open Workspace Settings (JSON) to modify workspace specific settings (recommended). Run Preferences: Open User Settings (JSON) to modify global user settings.

At this point, for the Trackyverse, there is no futher setup needed, however, for more on using Air to its full capacity, see the Air Guide.

Customizing Air

The air.toml file is a Tom’s Own Markup Language (.toml) file that allows users to customize and change the default settings of Air.

Below are the available settings to adjust and customize and can be added to to air.toml file:

[format]
line-width = 80
indent-width = 2
indent-style = "space"
line-ending = "auto"
persistent-line-breaks = true
assignment-style = "arrow"
exclude = []
default-exclude = true
skip = []
table = []
default-table = true
